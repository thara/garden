# Adaptive Software Synthesis

> **Turn dynamic computation into reusable software without losing the ability to adapt.**
>
> 動的な計算を再利用可能なソフトウェアへ変換しながら、変化への適応能力を維持する。

## 1. Motivation

従来のソフトウェア開発では、人間が問題を分析し、再利用可能な処理を設計・実装する。

実行時には、あらかじめ作成されたプログラムが入力に応じて処理を行う。

一方、AI Agentは、目的に応じて実現方法を動的に探索し、Toolを組み合わせ、必要に応じてコードを生成しながら問題を解決できる。

この柔軟性は、事前にすべての処理を実装する必要を減らす可能性がある。

しかし、毎回Agentが同じ問題を解き直すことが合理的とは限らない。

例えば、あるAgentが繰り返しデータを取得し、変換し、検証し、結果を出力しているとする。

その処理が安定しているなら、毎回推論によって手順を構成する代わりに、専用のプログラムとして実装した方が、実行速度、コスト、再現性、検証可能性の面で有利になる可能性がある。

この発想には、JITコンパイル、部分評価、プログラム合成、メモ化、プロファイルガイド最適化など、既存の計算機科学との接点がある。

ただし、Agentによる計算は、従来のプログラムとは異なる特徴を持つ。

- 処理手順が事前に固定されていない
- 同じ目的でも異なる手順が選ばれる
- 実行中に新しい情報を発見する
- 目的や制約が変化する
- 外部システムとの相互作用を含む
- 正しさを実行履歴だけから判断できるとは限らない

したがって、過去の実行を単純にコードへ変換するだけでは不十分である。

**どの計算を固定できるのか、何を一般化できるのか、どのように正しさを確かめるのか、いつ再び動的な実行へ戻すべきなのか。**

これらを一体として考える必要がある。

## 2. Central Question

**How can dynamically constructed computation be transformed into reusable software while preserving correctness and adaptability?**

動的に構成される計算を、正しさと適応能力を維持しながら、どのように再利用可能なソフトウェアへ変換できるか。

この研究では、Agentが生成したコードそのものを目的としない。

目的は、**動的な問題解決と、安定したソフトウェア実行の間を、必要に応じて移行できる計算基盤**の可能性を探ることである。

一度生成したソフトウェアを永久に使い続けることも前提としない。

実行条件、仕様、依存関係、利用頻度などが変化すれば、再検証、再生成、別実装への切り替え、動的な実行への復帰が必要になる可能性がある。

## 3. Conceptual Model

Adaptive Software Synthesisを、五つの観点から考える。

### Observation — どの計算が行われているか

動的な実行から、再利用や最適化の候補となる計算を把握する。

実行履歴、Toolの呼び出し、入力と出力、コスト、実行時間、失敗の傾向などが観測対象になる。

ただし、観測された振る舞いが、そのまま正しい仕様を意味するわけではない。

研究対象には以下が含まれる。

- Execution Tracing
- Behavioral Profiling
- Repeated Pattern Detection
- Cost and Latency Profiling
- Workload Characterization
- Candidate Identification

### Abstraction — 何を再利用可能な処理として切り出すか

個々の実行から、特定の入力や状況に依存しない処理を抽出する。

例えば、固定された値をパラメータ化する、複数の操作を一つの処理へまとめる、共通する計算を識別する、といった方法が考えられる。

研究対象には以下が含まれる。

- Generalization
- Parameterization
- Program Slicing
- Partial Evaluation
- Dependency Analysis
- Reusable Unit Identification

### Synthesis — どのように実装するか

抽出された計算を、再利用可能なソフトウェアとして具体化する。

実装方法はコード生成に限らない。既存のToolの組み合わせ、クエリの生成、実行計画の固定、専用の実行形式への変換なども候補になる。

研究対象には以下が含まれる。

- Program Synthesis
- Code Generation
- Program Specialization
- Tool Composition
- Execution Plan Optimization
- Implementation Selection

### Validation — 何を根拠に採用するか

生成された実装が、要求される性質を満たしているかを評価する。

実行履歴との一致は参考情報になるが、それだけで正しさを保証できるわけではない。

対象の仕様、契約、環境条件に基づく検証が必要となる。

研究対象には以下が含まれる。

- Contract Conformance
- Differential Testing
- Property-based Testing
- Static and Formal Verification
- Sandbox Evaluation
- Verification Evidence

### Adaptation — いつ更新・交換・破棄するか

生成された実装を、実行環境や要求の変化に応じて維持する。

仕様の改訂、依存関係の変更、入力分布の変化、コスト構造の変化などによって、以前の実装が最適または適切でなくなる可能性がある。

研究対象には以下が含まれる。

- Implementation Lifecycle
- Versioning
- Revalidation
- Regeneration
- Deoptimization
- Fallback to Dynamic Execution
- Cost-aware Adaptation

これらは必ずしも一方向の処理段階ではない。

新しい実装の評価結果が候補の選定方法を変えたり、実行環境の変化によって抽象化そのものを見直したりする可能性がある。

## 4. Research Principles

### 観測された振る舞いと仕様を区別する

過去の実行が成功していても、その処理があらゆる入力や環境で正しいとは限らない。

実行履歴は候補の発見や評価に利用するが、正しさの基準は対象の仕様や契約に置く。

### 再利用する単位を固定しない

再利用の対象は、単一の関数、複数のToolを組み合わせた処理、実行計画、サービスなど、さまざまな粒度になり得る。

特定のTool形式やコード生成方式を前提としない。

### 最適化と正しさを区別する

実行時間や推論コストが改善しても、要求される性質が失われていれば採用できない。

性能・コスト上の利点と、契約への適合性は独立して評価する。

### 生成した実装を永続的な正解とみなさない

生成されたソフトウェアは、特定の仕様、依存関係、環境条件の下で有効な実装である。

それらの条件が変化した場合は、保証や最適性を再評価する。

### 動的な実行への復帰を許容する

すべての計算を固定されたソフトウェアへ変換する必要はない。

不確実性が高い処理や変化の激しい処理については、Agentによる動的な実行を維持する方が合理的な場合もある。

## 5. Research Hypotheses

以下は、現時点で検証されていない技術的仮説である。

### H1. Agent-native JIT

Agentによる実行を観測し、安定した計算の候補を抽出して、検証可能な実装へ変換することで、動的な問題解決の一部を効率的なソフトウェア実行へ移行できるのではないか。

想定する循環は次のとおり。

1. 目的と制約を定義する
2. Agentの実行を観測する
3. 再利用候補を特定する
4. 計算を抽象化する
5. 実装を生成・選択する
6. 契約に照らして検証する
7. 再利用可能な実装として配備する
8. 実行状況に応じて再評価する

この循環を、仮にAgent-native JITと呼ぶ。

ただし、従来のJIT Compilerと同じ意味でのコンパイルが成立するかは、研究対象である。

### H2. Contract-preserving Specialization

入力条件や利用状況に応じて実装を特殊化することで、要求される契約を維持しながら実行効率を改善できるのではないか。

### H3. Evidence-based Reuse

仕様、検証結果、実装のRevision、依存関係、実行環境を関連付けることで、生成されたソフトウェアを安全に再利用・再評価できるのではないか。

### H4. Cost-aware Synthesis

生成・検証・維持に必要な費用と、将来の再利用によって得られる利益を比較することで、どの計算をソフトウェア化すべきか判断できるのではないか。

### H5. Adaptive Deoptimization

仕様や環境条件の変化によって実装の適合性が失われた場合、固定された実装から動的な実行へ戻すことで、適応能力を維持できるのではないか。

## 6. Research Directions

### Workload Discovery

Agentの実行から、どのような特徴を持つ処理が再利用に適しているか。

繰り返し頻度だけでなく、入力の安定性、処理の複雑さ、外部依存、変化の頻度などを考慮する。

### Program Abstraction and Specialization

動的な実行を、どのような単位で抽象化・特殊化すべきか。

個別の実行から一般的な処理を抽出する際、何を固定し、何をパラメータとして残すべきか。

### Synthesis and Optimization

既存のToolの合成、コード生成、実行計画の固定など、どの実現方法が適切か。

生成すること自体が目的ではなく、実装の再利用性、検証可能性、性能、維持費用を比較する。

### Verification and Evidence

生成された実装の正しさを、どのように検証するか。

検証結果がどの仕様、入力範囲、依存関係、実行環境に対して有効なのかを明確にする。

### Runtime Adaptation

生成した実装を、いつ利用し、いつ再検証し、いつ破棄するか。

実行時の条件に応じた実装方式の選択やフォールバックの仕組みを検討する。

### Economics of Software Synthesis

動的な推論による実行と、ソフトウェアの生成・検証・維持の費用をどのように比較するか。

実行回数、推論コスト、検証費用、変更頻度などを考慮し、再利用の経済合理性を評価する。

## 7. Initial Experiment

### Reusable Computation from Agent Execution

最初の実験候補として、Agentが繰り返し実行する限定されたデータ処理を、再利用可能な実装へ変換する。

目的は、完全自動のAgent-native JITを構築することではない。

**動的な実行を固定されたソフトウェアへ変換する際に、どのような情報、検証、費用が必要になるかを明らかにする。**

#### Experimental Setup

閉じた環境で、Agentが繰り返す定型的なデータ変換を対象とする。

最初は候補の選定を手動で行い、候補発見の自動化を独立した研究課題として扱う。

対象の仕様と契約を定義し、Agentによる動的な実行と、生成された実装を比較する。

#### Evaluation

- 生成された実装が契約を満たすか
- 動的な実行と比較して実行時間が改善するか
- 推論コストがどの程度削減されるか
- 生成・検証に必要な初期費用はいくらか
- 何回再利用すれば初期費用を回収できるか
- 入力条件や仕様が変化した場合、どのような再検証が必要か
- 動的な実行へのフォールバックが可能か

#### Expected Outcome

動的な計算をソフトウェアとして再利用する際の成立条件と、コスト・検証・適応性のトレードオフを整理する。

## 8. Open Research Questions

- どのような計算がソフトウェア化に適しているか。
- 実行履歴から再利用可能な処理をどのように識別するか。
- 個別の実行を一般化する際、どのように過剰な一般化を防ぐか。
- Agentによる推論のどの部分を固定できるか。
- 外部副作用を伴う処理をどこまで安全にソフトウェア化できるか。
- 生成された実装が仕様を満たすことを、どのような証跡で示すか。
- 仕様や依存関係が変化したとき、どの検証結果を無効化すべきか。
- 生成・検証・維持の費用を含めた最適化をどう行うか。
- 生成された実装をいつ破棄し、動的な実行へ戻すべきか。
- 既存のJITコンパイル、部分評価、プログラム合成、プロファイルガイド最適化と比較して、Agent-nativeな計算に固有の課題は何か。

## 9. Relationship to Other Research

### Trustworthy Autonomous Execution

生成された実装も、既存のToolと同じ権限、実行時制約、副作用の統制を受ける。

ただし、生成されたソフトウェアに特別な実行上の地位を与える必要はない。

### Specification-driven Computing

仕様は、生成された実装の正しさや交換可能性を評価する基準となる。

ただし、仕様の表現・検証そのものと、どの計算をソフトウェア化するかの判断は、異なる研究課題である。

### Unified Computational Model

動的なAgent実行と固定されたソフトウェア実行を、共通の計算モデルで扱える可能性がある。

ただし、特定のExecution UnitやActor Modelを前提としない。
