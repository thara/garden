# Specification-driven Computing

> **Specify what must hold, not necessarily how to achieve it.**
>
> 実現方法を記述する代わりに、成立すべき性質を定義する。

## 1. Motivation

従来のプログラミングでは、人間がアルゴリズムや処理手順を記述し、コンピュータがそれを実行することが基本となってきた。

一方、宣言的プログラミング、制約プログラミング、形式仕様記述、プログラム合成などは、実現方法よりも結果や性質を記述する方向へとプログラミングを発展させてきた。

例えば、SQLでは取得したいデータの条件を記述し、クエリの実行計画はデータベースが決定する。制約ソルバーでは、満たすべき条件を定義し、それを満たす解を探索する。

これらは、実現方法の一部をコンピュータに委ねる既存の例である。

AI Agentは、この考え方をさらに一般化できる可能性を持つ。

人間が目的と制約を与え、Agentが実現方法を探索し、既存の処理を組み合わせ、新たなコードを生成する。

ただし、実現方法を委ねるほど、その結果が意図した性質を満たすことを確認する仕組みが重要になる。

自然言語で表現された目的には曖昧さがあり、形式仕様にも記述漏れや誤りが存在し得る。

また、計算の正しさは入出力だけで決まるとは限らない。副作用、権限、性能、実行環境、外部システムとの相互作用も重要になる。

**実装手順から仕様へとプログラミングの中心を移すためには、何を仕様として表現し、何を検証し、何を実行時に保証できるのかを明らかにする必要がある。**

## 2. Central Question

**What does it mean to program a computer by specifying what must hold, rather than how to achieve it?**

実現手順ではなく、成立すべき性質を記述することで、コンピュータをプログラムするとはどういうことか。

この研究では、仕様を単なるドキュメントやコード生成の入力として扱わない。

仕様を、実装の選択、生成、検証、交換、合成の基準となる第一級の成果物として扱う可能性を探る。

目指すのは、あらゆる目的を完全な形式仕様として記述することではない。

人間が明示できる性質と、探索を通じて具体化される性質を区別しながら、実現方法をシステムに委ねられる範囲を広げることである。

## 3. Conceptual Model

Specification-driven Computingを、四つの観点から考える。

### Intent — 何を達成したいのか

人間が与える目的や要求を扱う。

目的は自然言語で表現されることもあれば、型、論理式、制約条件として記述されることもある。

また、最初から完全に定義されているとは限らず、探索や実行を通じて具体化される場合もある。

研究対象には以下が含まれる。

- 自然言語による目的の表現
- 要求の曖昧さと不完全性
- 目的の具体化と改訂
- 目的と検証可能な条件の対応付け
- 人間とAgentによる仕様の共同形成

### Contract — 何が成立しなければならないか

目的を、実装が満たすべき性質として表現する。

例えば、入力と出力の型、事前条件、事後条件、不変条件、許可されるEffectなどが考えられる。

ただし、すべての性質を同じ形式で表現できるとは限らない。

研究対象には以下が含まれる。

- Type System
- Preconditions / Postconditions
- Invariants
- Effect Systems
- Temporal Properties
- Resource Constraints
- Protocol Contracts
- Environment Assumptions

### Realization — どのように実現するか

仕様を満たす実装を、選択、生成、構成する。

実装は人間が書いたコードでも、Agentが生成したコードでも、既存のToolや外部サービスでもよい。

重要なのは、実装の由来ではなく、要求される契約との適合性である。

研究対象には以下が含まれる。

- Program Synthesis
- Implementation Selection
- Implementation Substitution
- Composition
- Runtime Adaptation
- Implementation Versioning

### Assurance — なぜ正しいと判断できるか

実装が仕様を満たすことを、どのような根拠で判断できるかを扱う。

型検査、静的解析、形式的証明、テスト、実行時検査、外部システムの契約、評価などは、それぞれ異なる性質を保証する。

研究対象には以下が含まれる。

- Static Verification
- Formal Verification
- Property-based Testing
- Runtime Verification
- Conformance Testing
- Verification Evidence
- Assumptions and Limitations

これらの観点は、必ずしも一方向の処理段階を意味しない。

実装の探索中に仕様が修正されることもあれば、検証の失敗によって要求の曖昧さが明らかになることもある。

## 4. Research Principles

### 仕様と実装を分離する

仕様は、特定の実装に依存しない形で成立すべき性質を表現する。

ただし、性能や外部環境など、実装条件に依存する性質も存在するため、必要な前提条件は明示する。

### 仕様の不完全性を前提とする

仕様は常に完全であるとは限らない。

未定義の振る舞い、曖昧な要求、検証できない性質を明示し、必要に応じて仕様を具体化する。

### 検証可能性と表現力のトレードオフを認識する

表現力の高い仕様が、必ずしも効率的に検証できるとは限らない。

何を形式的に証明でき、何を実行時に検査し、何を経験的に評価するのかを区別する。

### 実装の交換可能性を契約によって判断する

同じインターフェースを持つことと、同じ契約を満たすことは異なる。

実装を交換する際には、機能的な振る舞いだけでなく、副作用、性能、環境条件など、必要な性質が維持されるかを評価する。

### 仕様の合成可能性を重視する

個々の実装が契約を満たしていても、組み合わせたシステム全体が要求を満たすとは限らない。

契約の合成、Effectの伝播、共有状態、外部環境への依存を考慮する。

## 5. Research Hypotheses

以下は、現時点で検証されていない技術的仮説である。

### H1. Specification as a First-class Artifact

仕様を独立した成果物として管理することで、実装の生成、検証、交換を一貫した基準で扱えるのではないか。

### H2. Progressive Formalization

自然言語の目的を、型、制約、事前条件、事後条件などへ段階的に具体化することで、完全な形式仕様を最初から要求せずに検証可能性を高められるのではないか。

### H3. Contract-based Implementation Substitution

実装の生成元や内部構造に依存せず、契約への適合性を評価することで、異なる実装方式を交換可能にできるのではないか。

### H4. Composable Guarantees

契約とEffectを明示的に表現することで、複数の実行単位を合成した際に成立する保証を、一定の範囲で導出できるのではないか。

### H5. Evidence-aware Execution

検証結果とその前提条件を仕様・実装に関連付けることで、実行環境や依存関係の変更に応じて、保証の有効性を再評価できるのではないか。

## 6. Research Directions

### Specification Languages

目的、制約、契約を表現するために、どのような言語や形式が適切か。

自然言語、型、論理式、DSLなどをどのように組み合わせるべきか。

### Formal Methods and Verification

形式仕様から、どのような性質を証明・検査できるか。

既存の形式手法を、Agentが生成・選択する実装にどのように適用できるか。

### Contract Composition

複数の契約を組み合わせたとき、どのような性質が維持されるか。

特に、Effect、共有状態、非同期実行、外部システムとの相互作用をどう表現するか。

### Implementation Independence

仕様を満たす複数の実装を、どのように比較・選択・交換するか。

実装の性能、コスト、信頼性、実行環境への依存をどう評価するか。

### Specification Evolution

目的や制約が変化したとき、仕様、実装、検証証跡をどのように更新するか。

仕様の改訂が既存の保証に与える影響をどう判断するか。

## 7. Initial Experiment

### Contract-based Implementation Substitution

最初の実験候補として、限定された仕様に対して複数の実装を用意し、同じ契約によって検証・交換できるかを調べる。

目的は、包括的な仕様言語やProgram Synthesisシステムを構築することではない。

**仕様を実装から独立させたとき、何を機械的に保証でき、何が保証の外側に残るのかを明らかにする。**

#### Experimental Setup

副作用のないデータ変換処理を対象とする。

入力・出力の型、事前条件、事後条件、不変条件を定義する。

人間が記述した実装と、Agentが生成した実装を用意する。

#### Evaluation

- 同じ契約で複数の実装を検証できるか
- 型検査、テスト、形式的検証でそれぞれ何を検出できるか
- 契約が不完全な場合、どのような誤実装を見逃すか
- 契約を変更したとき、どの検証証跡を再利用できるか
- 実装の交換可能性をどの範囲で主張できるか

#### Expected Outcome

契約の表現力、検証可能性、実装の交換可能性の関係を整理する。

また、仕様を第一級の成果物として扱う際に必要な情報と、その限界を明らかにする。

## 8. Open Research Questions

- 仕様の最小構成要素は何か。
- 自然言語による目的を、どの段階で形式的な契約へ変換すべきか。
- 仕様の曖昧さや不完全性をどのように表現するか。
- Agentが仕様の具体化に関与する場合、その妥当性を誰が判断するか。
- 契約への適合性をどのような証跡で示すか。
- 機能的な正しさと、性能・コスト・信頼性の保証をどう統合するか。
- Effectや外部環境への依存をどのように仕様化するか。
- 複数の契約を合成したとき、どのような保証が維持されるか。
- 仕様変更時に、どの検証結果を無効化すべきか。
- 既存の宣言的プログラミング、形式仕様、Program Synthesisと比較して、Agentが加わることで何が新しく可能になるか。

## 9. Relationship to Other Research

### Trustworthy Autonomous Execution

仕様で定義された権限やEffectの制約は、実行時の統制に利用できる。

ただし、完全な形式仕様がなくても、実行時の権限制御や副作用の統制は成立し得る。

### Adaptive Software Synthesis

生成されたコードを検証する際、仕様は実装の正しさを評価する基準となる。

ただし、仕様を中心とするプログラミングモデルは、自動コード生成を前提としない。

### Unified Computational Model

実行単位の契約や合成規則を表現するための基盤となる可能性がある。

ただし、仕様の表現方法と実行単位の具体的な計算モデルは、独立した研究課題として扱う。
